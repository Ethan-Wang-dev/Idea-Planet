# Idea Planet · 后端与 Agent 实现路线

更新时间：2026-09-06

本文以当前代码为基准，区分已经存在的本地能力、半实现能力和后端化后需要补齐的模块。

## 当前已经完成

### 采集与内容关系

- Chrome Manifest V3 插件监听 X 的 Like、Bookmark、发帖和回复提交。
- 页面已打开时自动导入，页面未打开时进入插件本地队列。
- 普通帖子和 X Article 的正文采集、`Show more` 展开和噪声清洗。
- 同一 URL / capture key 去重，并保留 Like 与 Bookmark 等来源信号。
- 用户自己的回复、引用评论与原帖之间有父子关系字段。
- 长帖重新采集时可以升级旧正文，并保留用户已有的想法和状态。
- 引用帖原帖的自动捕捉仍不稳定；下一次处理应研究结构化网络响应或 `quoted_status`，不再继续堆叠 DOM 选择器。

### 本地 Planet

- Planet、Timeline、All ideas 三个视图。
- 内容搜索、轻量标签、标签 Board 和固定 Board。
- Sweep、恢复、从当前内容产生新的 Idea、标签编辑。
- Idea 正文和标题的行内编辑。
- 长内容折叠 / 展开、来源标记、原帖链接和回复原帖展示。
- JSON 导出和 `localStorage` 持久化。
- 本地单用户数据模型和种子数据。

### 工程验证

- 长帖、Article、重复采集、正文升级和插件队列有回归测试。
- 当前 `server.mjs` 能提供静态网页，但不是业务后端。

## 半实现或需要校正的部分

### 已废弃的 Practice / Action 模型

`Practice`、`Action` 不再是产品中的独立对象，也不是后端待补齐的功能。产品已经确定采用“一切皆为 Idea”的框架：行动、实践目标、实践结果、新问题和长期观点都只是不同语义的 Idea，可以通过标签、关系和正文表达。

因此后端不应建立独立的 `practices` 或 `actions` 表，也不应把 `practice: { goal, due, result, done }` 继续作为核心契约。旧数据中的字段仅作为迁移兼容，后续逐步转换或忽略。

### 文档与当前代码

- README 和 02 MVP 文档已改为以 Idea 延伸表达行动、结果和新问题。
- 当前代码使用 `localStorage`，没有账号、同步、云端数据隔离或服务端 API。

## 尚未实现的功能

### P0：云端数据基础

这是 Agent 之前必须先完成的基础层：

- 用户注册、登录、会话和账户删除。
- 每个用户的 Idea、标签、Board、关系和任务数据隔离。
- 云端数据库、迁移、索引和版本化 API。
- 从 `localStorage` 导入到云端，以及冲突处理和离线重试。
- 跨设备同步。
- 附件 / 图片 / 音视频对象存储。
- 数据导出、删除、备份、恢复和隐私设置。
- 服务端 API 的鉴权、限流、审计日志和错误追踪。

Idea 更新使用 revision 和增量 change cursor；删除保留墓碑，避免多设备同步时把已删除内容重新带回。

建议核心关系至少包括：

```text
users
ideas
idea_sources
idea_relations
tags
boards
board_items
agent_tasks
agent_runs
agent_outputs
usage_ledger
```

### P0：Agent 最小闭环（骨架已开始）

第一版 Agent 不需要一开始实现多个独立人格。当前已经有不调用外部模型的本地 Recall runner，用来验证任务、上下文、事件和输出契约。完整闭环仍需补齐：

1. 用户输入任务目标，例如“帮我写一篇关于 AI 产品审美的文章”。
2. 系统识别任务类型：Recall、Synthesize、Draft、Action 或 Research。
3. 从用户的 Idea 中召回候选内容。
4. 对候选内容排序、去重并生成上下文包。
5. 调用模型生成结构化结果。
6. 将结果、引用的 Idea、提示词版本和使用量保存为 `agent_output`。
7. 用户可以编辑结果，并一键保存为新的 Idea。

第一版的关键不是“聊天体验”，而是结果是否能够回到 Planet，并保留来源和可追溯关系。

### P0：Agent 基础设施

- 模型 Provider 适配层，不把 OpenAI / Anthropic / Google 的调用散落在业务代码里。
- Prompt 模板和版本管理。
- 结构化输出 schema 和 JSON 校验。
- embeddings 生成、更新和删除。
- 全文搜索 + 向量搜索 + 时间 / 标签 / 来源过滤的混合检索。
- 任务队列、重试、超时、取消和幂等。
- 流式输出。
- 每次任务的输入、输出、模型、耗时、错误和 credits 记录。
- 低成本模型与高质量模型的路由策略。

### P1：Idea 智能层

- 自动建议标签，但必须允许用户拒绝和修改。
- 低价值密度候选的弱化建议，不直接删除。
- 主题聚类、相似 Idea、递进、冲突和重复观点。
- 用户观点画像和偏好摘要。
- 在合适时机提示旧 Idea，而不是单纯按时间推送。
- 从多个 Idea 生成研究路径、选题、决策备忘录或行动建议。

### P1：外部研究与工具

- 联网搜索和网页抓取。
- 外部来源的引用、时间和链接保存。
- 研究任务的多步执行和中间结果。
- 日历、邮件或第三方工具集成。
- 浏览器 Agent / MCP 工具调用。

这些能力必须晚于最小 Recall / Draft 闭环。否则会先得到一个昂贵但无法证明个人上下文价值的通用 Agent。

### P1：账户、订阅和 credits

- 套餐和权限模型。
- AI credits 余额、预扣、结算、退款和失败任务回滚。
- `usage_ledger`：任务类型、模型、消耗、时间和结果状态。
- 附件容量、带宽和转录配额。
- 补充 credits 和账单页面。
- 支付平台、Webhook、订阅变更和发票。

采集、编辑、普通搜索、标签和导出不应扣 credits。credits 只用于可变成本的 AI 任务。

### P1：安全与信任

- 把用户保存的 X 内容视为不可信输入，防止 prompt injection 影响 Agent 行为。
- 工具调用必须经过显式权限、域名 allowlist、超时和资源限制。
- 联网任务要防 SSRF、任意文件访问和凭证泄露。
- Agent 不能未经确认发布内容、发送邮件、修改外部服务或删除用户数据。
- 记录 Agent 的来源、动作和用户确认点。
- 明确模型供应商是否保存数据、是否用于训练以及用户的数据删除政策。

### P2：Idea 回访与外部提醒

- 对带有时间语义的 Idea 提供可选的回访日期。
- 系统通知、邮件或日历提醒。
- 到期前重新召回相关 Idea。
- 回访记录作为新的 Idea 保存，并与原始 Idea 建立关系。

## 推荐实现顺序

### 阶段 1：先建立 API 和数据契约

- 确定 `Idea`、`Relation`、`AgentTask`、`AgentOutput` 和 `UsageEvent` schema。
- 保留当前 localStorage 导出格式，写导入器和迁移版本。
- 把本地静态服务器升级为 API 服务，但先不接模型。

### 阶段 2：云端同步闭环

- 单用户账户。
- Idea / tags / relations 的 CRUD API。
- 插件通过用户会话上传采集结果。
- 网页从 API 读取和写入，不再直接依赖 localStorage。
- 完成导入、导出、冲突和离线队列。

### 阶段 3：可替换的 Agent Kernel

- `POST /agent/tasks` 创建任务，但 API 不绑定某一种 Agent 框架。
- 将 Agent 拆成可替换的 `definition`、`context builder`、`model provider`、`tool registry`、`policy`、`run state` 和 `output adapter`。
- 召回用户 Idea，形成版本化的 context package。
- 调用一个模型 Provider，保留模型和 Prompt 版本。
- 流式返回结果，同时持久化可恢复的 run state。
- 输出保存为可编辑的 Agent Output。
- 一键保存为新 Idea，并保留引用关系。
- 支持以后把单次调用改造成多步图、循环、并行、人工确认或完全不同的 Agent 运行模型，而不破坏外部 API。

### 阶段 4：安全、可靠性和可观测性

- 队列、重试、幂等、超时、取消和任务状态。
- Provider fallback。
- Agent 工具权限、输入隔离和人工确认点。
- 真实 usage ledger 和 credits 预扣 / 结算接口，但暂不把商业 UI 作为主线。
- 检索质量、提示词注入、权限边界和成本回归测试。

### 阶段 5：智能化和外部工具

- 自动标签、关系、低价值弱化和定时召回。
- 联网研究、浏览器工具和提醒。
- 在有真实用户任务数据后，再增加多 Agent / 自定义 Agent。

## Agent 可演进性原则

由于 Agent 仍在学习和探索阶段，第一版不要把产品设计锁死在“一个聊天接口 + 一套系统 Prompt”上。

- **外部 API 稳定，内部运行模型可变**：任务创建、状态查询、取消、流式事件和输出保存保持稳定；内部可以从单次调用演进到图、循环、并行和人工确认。
- **Agent 定义版本化**：名称、目标、指令、可用工具、权限和模型策略都要有版本，不要覆盖旧运行记录。
- **上下文独立于 Agent**：召回结果、用户选择、引用片段和上下文预算组成独立的 context package，便于更换 Agent 推理方式。
- **工具独立于推理**：工具只暴露类型化输入输出和权限声明，不直接依赖某个模型 Provider。
- **运行可恢复、可重放**：保存事件、状态转移、输入摘要、输出和错误，便于调试、评估和更换模型后重跑。
- **保留人工介入点**：涉及外部副作用、敏感内容或不确定判断时，可以暂停并等待用户确认。
- **模型 Provider 可替换**：模型调用统一放在 adapter 层，业务逻辑不直接依赖单一供应商。
- **先做单 Agent Kernel，再做多 Agent**：只有在单 Agent 的检索、工具、状态和输出契约稳定后，才引入角色协作和 Agent 之间的委派。

## 第一版 Agent 的验收标准

不以“能聊天”为验收标准，而以以下闭环为准：

1. 用户提出一个真实的写作、判断或行动任务。
2. 系统从 Planet 中找到可解释的相关 Idea。
3. 输出中能够看到引用来源，而不是无来源的泛泛回答。
4. 用户可以编辑输出并保存为新的 Idea。
5. 新 Idea 与任务和来源 Idea 可追溯。
6. 任务失败时不会重复扣费，也不会污染 Planet。
7. 用户能看到任务消耗和结果，但不需要理解 token。
